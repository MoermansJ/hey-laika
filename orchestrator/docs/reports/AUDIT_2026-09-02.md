# hey-laika project audit — 2026-09-02

**Auditor:** Claude Fable 5.1 (the code was written with Claude Fable 5.0).
**Scope:** `orchestrator/` (Spring Boot + static GUI), `dog/` (Flask adapter), the
`opencat-esp32/` hey-laika firmware fork, and `orchestrator/docs/`.
**Method:** both test suites run; four parallel deep reads (orchestrator Java,
adapter Python, firmware diff vs upstream base `9ebb48a`, GUI + docs); every
high-severity claim re-verified by me against the source before it went in
here; live evidence taken from the running stack (container logs, activity
log, network probes). Nothing was modified.

Severity scale: **Critical** = can damage hardware or is a data-loss/security
hole reachable today; **High** = wrong behaviour the owner will hit in normal
use; **Medium** = latent bug or waste; **Low** = hygiene.

---

## 1. Executive summary

The project is in better shape than most solo robotics codebases: the
architecture is coherent (thin Java coordinator, one Python adapter owning
hardware, a host-controlled firmware), comments cite validation dates, and both
suites are green (31 Java tests, 124 Python tests). The design briefs are
unusually good at recording *why*.

The problems cluster in three places:

1. **Two independent "who owns motion" gaps.** The orchestrator's behaviour
   loop can still be driving servos after `stop()` returns, and the adapter's
   WiFi retry can re-send a skill that is still executing. Both can put two
   motion commands on the servos at once. The adapter's arbiter is described
   as the single motion owner but four HTTP routes bypass it.
2. **A GUI wiring bug with a hardware consequence.** On Mocha's robot page the
   Control and Voice tabs silently drive Laika. Plus eight unescaped
   `innerHTML` sinks fed by LLM output and user text.
3. **Documentation drift.** Three different descriptions of which firmware is
   flashed, two README endpoint tables that cover a third of the routes, and a
   superseded firmware roadmap (four `FIRMWARE_*.md` files) still at the top
   level of `docs/`.

None of the findings is a "rewrite it" verdict. The top nine fixes in §8 are
each under two hours.

### Scorecard

| Area | Verdict | Biggest issue |
|---|---|---|
| Orchestrator (Java) | Solid, over-provisioned | Behaviour loop `stop()` does not join its thread |
| Adapter (Python) | Good, some sharp edges | WS retry may double-execute motion; idle ladder never reaches "rest" |
| Firmware fork | Phase A mostly real, Phase B/C not started | A queued WebSocket task is wiped before it runs; no abort path from the host |
| GUI | Functional, fragile | Wrong-robot bug on embedded tabs; XSS sinks; polling never stops |
| Docs | Rich but drifting | Firmware status stated three different ways |
| Tests | Green, uneven | Riskiest classes (`RobotBehaviorLoop`, WS retry path) untested |
| Ops / repo hygiene | OK for a home LAN | No CI, unpinned Python deps, root containers, debug server on 0.0.0.0 |

## 2. Orchestrator (`orchestrator/src/main/java`)

**Architecture.** REST controllers resolve a `RobotAgent` from the in-memory
`FleetManager` and delegate every call to `PythonServiceClient` (3 s connect,
30 s read). `FleetBroadcaster` polls the adapters on `@Scheduled` sweeps and
pushes over STOMP. `RobotBehaviorLoop` runs one daemon thread per robot
(decide → execute → update) with `RuleBasedDecisionEngine`. JPA/Postgres holds
a `robots` table and hourly metric rollups.

state manager, `FleetManager`, broadcaster gating and controller proxying are
covered. `RobotBehaviorLoop` (the riskiest class), `PythonServiceClient` error
mapping, `MetricsService` and `FleetInitializer` have zero tests. One
regression test (`RuleBasedDecisionEngineTest.java:134-154`) passes only
because `0.6-0.5+0.05` rounds below the 0.15 threshold.

power/polling/senses/leash traffic and should be renamed. Dockerfile runs as
root; `ollama/ollama:latest` unpinned; Boot parent 3.5.5 sits behind the 3.5
line.

## 3. Adapter (`dog/app`)

**Architecture.** `app.py` is a module-level composition root: it opens SQLite,
builds one controller (mock / serial / WiFi), wraps `send_command` three times
(metrics → odometry → poll policy), then starts the arbiter thread, the
event-binder idle and battery loops, the leash watchdog, the WiFi sniffer, the
power tracker and the metrics flusher. Routes either talk to the controller
directly or submit stored behaviours to the `Arbiter`, whose single worker
serialises motion. Robot pushes (`event_*` frames) fan out to leash → binder
→ arbiter. All transports hold one RLock around write-and-await-completion.

**Dead / over-engineered.** The in-process `AutonomousLoop` + `ChoreographyLibrary`
+ Claude decision path is called "the deprecated old brain" at `app.py:503`
yet still ships three endpoints, DB tables and the Claude client.
`SystemConfiguration` and `ChoreographyEntry` models are unreferenced.
`robot_schema.py:98-110` reports every sensor `available: False` although
battery works.

**Tests.** Strong where it matters physically: `test_gait_learner.py`
(physics-scripted controller), `test_serial_controller.py` (real captures),
`test_behavior_framework.py` (pre-emption, provenance). Missing: the WS
timeout + heartbeat path, the idle pump, event frames mid-transaction, the
idle-ladder timing race (the existing test pre-sets the anchor and so cannot
see it), `/behaviors` + `/bindings` + `/greeting` + `/idle` routes,
`PowerTracker` against WiFi semantics, gait stop mid-turn. Several tests
mutate the shared module-level app and rely on wall-clock sleeps.

**Quality notes.** Duplicated 16-value `j` parsing, voltage regex, AP-line
parsing, timeout rule (`startswith(("k","K","X"))` ×4) and heading
normalisation. `requirements.txt` is entirely `>=`; no lock file. Dockerfile
runs as root, `python:3.11-slim` unpinned, `--workers 1` is load-bearing
(module-level singletons, firmware's 2-client cap) but undocumented. Comments
are unusually good and cite validation dates. The Claude call itself is
current: `fallbacks="default"` with the server-side-fallback beta and a
`refusal` stop-reason check.

### Host/firmware contract check

| Adapter assumes | Firmware does | Match |
|---|---|---|
| `response` frames with `running/completed/error` and a `results` list | Yes; the timeout frame lacks `type` but the adapter matches on `taskId` | Yes |
| `completed` means motion finished | Only for parameterised gaits; plain `kwkF` completes on echo | Partial (Cut 8) |
| One task at a time, 20 s skill budget | 45 s firmware timeout; the command sent after an adapter timeout silently hangs (F1) | **Mismatch** |
| Heartbeat every ≤20 s; firmware drops at 40 s | Yes; commands also refresh | Yes |
| `event_*` may interleave anywhere | RSSI broadcast to all clients | Yes |
| `EXCEPTION_REPORT` appears in `results` | Only while a task is active | Partial |
| Never re-send if the probe succeeds | Correct; with F1 a re-send would double-queue | Yes |

### Firmware improvements, ranked

1. **Fix the pending-task wipe** (tiny): defer `processNextWebTask()` to
   `WebServerLoop` via a flag, or make `resetCmd()` skip the clear when a web
   task was staged after entry. This unblocks the whole Cut 2 promise.
2. **Abort path over WS** (small): a `{"type":"abort"}` frame, or start
   `krest`/`kup`/`d` immediately and error the running task. Makes the host
   the real safety authority.
3. **`event_exception` push** (~15 lines): mirror `sendRssiData` from the
   report-once branch; `leash.py` and `event_binder.py` already consume
   `event_*`.
4. **Dead-man on heartbeat recency** (tiny): derive `wsAlive` from the newest
   `lastHeartbeat`, not from `!connectedClients.empty()`.
5. **Clear timed-out tasks and drain FIFO** (small): `clearWebTask` in the
   timeout loop; a `std::deque` of pending ids.
6. **Skip pushes when the socket is backed up** (small): drop the RSSI push if
   the previous `sendTXT` returned false.
7. **Compile-time trims for host-controlled use:** undefine `VOICE`,
   `QUICK_DEMO`, `PIR`, `DOUBLE_*`, `GESTURE`; zero `moduleActivatedQ` so
   Serial1/Serial2 are never opened and the 1.5 s voice sync is skipped; drop
   `BT_SSP` if unused (~50 KB heap and a boot scan). Put a fork suffix on the
   `?` banner's second line so the host can verify it is talking to the
   reflex-free build.
8. **Runtime SSID fallback:** alternate `WiFi.begin` between the two slots
   from `WebServerLoop` on prolonged disconnect, removing the reboot need.

## 7. Cross-cutting observations

**Repo and ops hygiene.**
- No CI. Both suites run in under a minute; a GitHub Actions workflow that
  runs `mvnw test` and `pytest` on push is the cheapest quality gate
  available.
- `.gitignore` is correct (no `.env`, `.db`, `target/` tracked). Good.
- Python dependencies are all `>=` with no lock file; the Docker build is
  irreproducible. `pip-compile` or a `requirements.lock` fixes it.
- Both containers run as root; `ollama/ollama:latest` and `python:3.11-slim`
  are unpinned.
- Hard-coded Postgres credentials and no API auth are fine on a trusted LAN;
  write that assumption down once so it is never accidentally violated by a
  port-forward.

**Fleet-of-one design.** The memory decision to design for Laika only is
mostly honoured, but the leftover genericity is where the bugs live:
`RobotAgent` mirroring the client, the write-only `robots` table, the
per-robot `parallelStream`, and the GUI's `robots[0]` default (the wrong-robot
bug). Mocha is a GUI fixture, not a fleet member; the code could say so.

**Motion ownership.** Three independent owners exist today: the orchestrator's
behaviour loop, the adapter's arbiter, and direct routes (`/command`,
`/servo`, `/execute_action`, gait learner). The 409 guard is pairwise and
racy. The fix with the best leverage is the one the behaviour brief already
names as Phase 4: the orchestrator submits through the arbiter, and direct
routes become arbiter submissions at manual priority.

**Today's runtime evidence (2026-09-02, UTC).** After the voice-module
commands at 09:42:41 and 09:45:58-59, Laika kept answering WiFi-scan commands
for six more minutes and went silent at 09:51:55 during a battery poll. Since
then she answers pings intermittently and refuses WebSocket connects, which
looks like weak signal or power-off rather than a firmware crash (the only
`ESP.restart()` paths are WiFi-manager failures). Two things the incident
exposed: the adapter logs "Power OFF snapshot" for what is really
"unreachable", and two reconnect loops (the status poller and the idle pump)
each retry with 3 s timeouts, so the log fills with identical errors at two
cadences.

**Voice module.** The Petoi module is soldered onto BiBoard V1 with its own
speaker; its "Bing-Bing"/"Di-Di" language phrases are matched inside the
module regardless of the mute command. Today the BiBoard-side module was
disabled with `Xa` (persisted in NVS). Silencing the module physically means
covering its mic or lifting a speaker lead; the voice relay brief no longer
depends on either.

## 9. Feature assessment and speculation

### Where each feature stands

| Feature | State | Evidence |
|---|---|---|
| Behaviour framework | Phase 1 done; Phase 2 builder-as-editor not started; Phase 3 events partial; Phase 4 agent-through-arbiter not done | `behavior_store.py:102-172`, `builder.js:255` still POSTs `/execute_action` |
| Proximity leash | Phases 1-3 largely done (RSSI push, dead-man, beacon, marks, GUI); walk-test validation not recorded | `leash.py`, `webServer.h:749-758` |
| Navigation | Senses layer + dead-reckoned pose exist; map, clustering, rooms, `goto_room` aspirational | `senses.py`, mind page |
| Voice | Text→Ollama demo only; hardware ordered; wake word / transcription aspirational | `voice.py`, `VOICE_RELAY_BRIEF.md` |
| Mind page | v0 done; map and "agent thoughts" panels absent | `mind.html` |
| Metrics | M1+M2 done incl. Postgres rollups; `/api/metrics/history` has no GUI consumer | `MetricsService.java` |
| Personality loop | Rule-based reflex works; LLM director absent; reachable only via the unlinked page | `RuleBasedDecisionEngine.java`, `behavior.html` |
| Power tracking | Tracker + `/power` route exist; no GUI consumer | `power.py` |

### What is missing for day-to-day enjoyment

The owner currently starts "being a dog" from a hidden page, and that mode
then fights manual control. The gaps, in order of how often they would be
felt:

1. **One switch: awake / asleep / be yourself.** A single mode on the robot
   header that starts the loop, arms idle ladder + greeting, and yields to
   any manual action (which needs fix #18 or at least #2).
2. **Home / away mode.** Named as "needed" in both the leash brief and the
   nav brief; gates leash arming, sniffer and idle ladder. All the data
   already exists in `leash.py` and `senses.py`.
3. **Schedule bindings.** Bedtime rest, morning stretch, "quiet hours" for
   the sniffer. `event_binder` already has the trigger shape; add a
   `schedule` event source and a tiny binding UI.
4. **A phone-friendly surface.** Tabs clip and iframes nest-scroll below
   600 px. A two-page mobile layout (status + four big buttons) would be used
   far more than the desktop console.
5. **Sound on the dog, not the PC.** A `sound:` step type driving `/sound`
   (already routed at `RobotController.java:133`) so greetings and leash
   warnings chirp from Laika. Cheap and delightful.

### Cheap ideas that fit the existing architecture

- **"Agent thoughts" on the Mind page** from `/behavior/history` reasoning,
  which is already stored.
- **Battery sparkline** on the dashboard from `/api/metrics/history`; rollups
  exist, nobody reads them.
- **"Do a trick" buttons** on the Activity tab that call
  `POST /arbiter/invoke`, so the arbiter (not a bypass route) owns them.
- **Real `/api/health`** aggregating adapter reachability, driving the nav
  dot that is currently always green.
- **A `Laika` capability flag file** (`capabilities.json`) generated from the
  firmware `?` banner and adapter schema, so the GUI hides tabs the robot
  cannot serve (Mocha shows a Voice tab it cannot honour).
- **Use the leash RSSI push for a "where is she" indicator** on the dashboard
  card (near / room / far), since the data already streams at 1 Hz.

### Refinements to existing features

- **Behaviour loop:** add per-action cooldowns and an energy budget so a
  bored dog does not backflip three times a minute; log the *decision inputs*
  alongside the choice so the Mind page can explain it.
- **Idle ladder:** make thresholds config-driven (the config keys exist and
  are unread) and expose them in the Behavior Lab editor that already exists.
- **Leash:** record the walk-test results the brief calls for, and treat
  "lost" on a transport without RSSI as "unsupported" rather than forcing
  rest.
- **Power tracker:** distinguish "unreachable" from "off"; open sessions on
  the first successful `P` poll, not on WebSocket connect.
- **Metrics:** price the model actually configured (read `CLAUDE_MODEL` from
  the adapter schema) instead of a fixed constant; add Ollama call counts so
  the default engine is visible too.
- **Decision engine:** the adapter's Claude call is well-formed but sends no
  `cache_control` on a stable system prompt and parses free text; structured
  output (`output_config.format`) would make `_parse_decision` unnecessary
  and cheaper. Only matters if Claude is ever switched on.

### Larger directions worth a brief before building

- **Move the personality director into the adapter and delete the Java
  loop.** The orchestrator would become what its README says: registry,
  proxy, GUI. One motion owner, one decision owner, one process to test.
- **Or the opposite:** keep the brain in Java and make the adapter a pure
  transport. Either is defensible; having both halves of a brain in two
  languages is the expensive middle.
- **Drop Postgres.** An H2 file (or SQLite in the adapter, which already has
  one) removes a container, a healthcheck gate and a credential. Rollups are
  two rows an hour.
- **Firmware:** with the host owning behaviour, the stock modules compiled in
  (gesture, PIR, double-touch, camera, ultrasonic) cost RAM and boot time for
  nothing. A `LAIKA_MINIMAL` build flag is a natural next cut.
